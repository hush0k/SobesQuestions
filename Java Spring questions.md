> [!question]- 1. В чём главный минус JPA?
> Главный минус — **JPA скрывает SQL**. Разработчик работает с объектами и не видит, какие запросы реально уходят в базу. Из-за этого легко написать код, который выглядит нормально, но генерирует десятки или сотни лишних запросов.
>
> **Самый известный пример — проблема N+1:**
> Загружаем 100 пользователей, у каждого есть список заказов с `FetchType.LAZY`. В цикле обращаемся к `user.getOrders()`:
> - 1 запрос на получение пользователей
> - +100 запросов, по одному на заказы каждого пользователя
>
> Итого 101 запрос вместо одного-двух.
>
> **Как решают N+1:**
> - `JOIN FETCH` в JPQL-запросе
> - `@EntityGraph` в Spring Data
> - `@BatchSize` — подгружает связи пачками через `IN (...)`
>
> **Другие минусы:**
> - **LazyInitializationException** — обращение к ленивой связи, когда сессия уже закрыта
> - **Накладные расходы** — persistence context хранит все загруженные сущности и делает dirty checking (сравнивает их состояние перед коммитом), при больших объёмах это память и время
> - **Сложные запросы** — аналитику, отчёты, оконные функции неудобно писать через JPA, для них лучше native SQL или jOOQ
> - **Неочевидное поведение** — каскады, `orphanRemoval`, двусторонние связи, `equals/hashCode` у сущностей легко настроить неправильно
>
> Поэтому важно включать логирование SQL (`spring.jpa.show-sql=true` или логгер `org.hibernate.SQL`) и проверять, какие запросы на самом деле выполняются.

> [!question]- 2. Какой синтаксис можно указать в @Query и как его писать?
> В `@Query` можно писать запросы на двух языках:
>
> **1. JPQL** (по умолчанию) — запрос пишется по **сущностям и их полям**, а не по таблицам и колонкам:
> ```java
> @Query("SELECT u FROM User u WHERE u.email = :email")
> Optional<User> findByEmail(@Param("email") String email);
> ```
> Здесь `User` — имя класса-сущности, `u.email` — поле класса. Плюс: не зависит от конкретной базы.
>
> **2. Native SQL** — обычный SQL по **таблицам и колонкам**, включается через `nativeQuery = true`:
> ```java
> @Query(value = "SELECT * FROM users WHERE email = :email", nativeQuery = true)
> Optional<User> findByEmailNative(@Param("email") String email);
> ```
> Нужен, когда требуются возможности конкретной СУБД: оконные функции, JSONB, `ON CONFLICT` и т.д.
>
> **Как передавать параметры:**
> - **именованные** — `:email` + `@Param("email")`. Рекомендуемый вариант, читается лучше
> - **позиционные** — `?1`, `?2` по порядку аргументов метода. Работает, но легко ошибиться при изменении сигнатуры
>
> **Изменяющие запросы** (UPDATE, DELETE) требуют `@Modifying` и транзакции:
> ```java
> @Modifying
> @Transactional
> @Query("UPDATE User u SET u.active = false WHERE u.lastLogin < :date")
> int deactivateInactive(@Param("date") LocalDateTime date);
> ```
> Без `@Modifying` Spring выбросит исключение, так как ждёт SELECT.
>
> **Пагинация:** в JPQL достаточно добавить `Pageable` в параметры. Для native-запроса с `Page` нужно дополнительно указать `countQuery`, иначе Spring не всегда сможет сам построить запрос на подсчёт.

> [!question]- 3. Что такое @EntityGraph и как с ним работать?
> `@EntityGraph` — способ указать, какие связи сущности загрузить **сразу, одним запросом через JOIN**, даже если они помечены как `LAZY`. Основное применение — решение проблемы N+1 без написания JPQL с `JOIN FETCH`.
>
> **Пример сущностей:**
> ```java
> @Entity
> public class User {
>     @Id
>     private Long id;
>
>     @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
>     private List<Order> orders;
> }
> ```
>
> **Способ 1 — прямо в репозитории через `attributePaths`** (самый частый):
> ```java
> public interface UserRepository extends JpaRepository<User, Long> {
>
>     @EntityGraph(attributePaths = {"orders"})
>     List<User> findAll();
>
>     @EntityGraph(attributePaths = {"orders", "orders.items"})
>     Optional<User> findById(Long id);
> }
> ```
> В `attributePaths` указываются **имена полей сущности**. Вложенные связи — через точку.
>
> **Способ 2 — именованный граф на сущности:**
> ```java
> @Entity
> @NamedEntityGraph(
>     name = "User.withOrders",
>     attributeNodes = @NamedAttributeNode("orders")
> )
> public class User { ... }
> ```
> ```java
> @EntityGraph("User.withOrders")
> List<User> findByActiveTrue();
> ```
> Удобно, если один и тот же граф используется в нескольких методах.
>
> **Работает и вместе с @Query:**
> ```java
> @EntityGraph(attributePaths = {"orders"})
> @Query("SELECT u FROM User u WHERE u.active = true")
> List<User> findActiveWithOrders();
> ```
>
> **Тип графа (`type`):**
> - **FETCH** (по умолчанию) — указанные поля грузятся сразу, все остальные как LAZY
> - **LOAD** — указанные поля грузятся сразу, остальные по своим настройкам из маппинга
>
> **Подводные камни:**
> - **Пагинация + коллекция** — Hibernate не может применить LIMIT к JOIN с коллекцией и делает пагинацию в памяти, выдавая предупреждение. На больших таблицах это опасно
> - **Две коллекции типа List** в одном графе — `MultipleBagFetchException`. Решения: использовать `Set` или грузить вторую коллекцию отдельно / через `@BatchSize`

> [!question]- 4. Аннотация @Transactional — что про неё можете рассказать?
> `@Transactional` говорит Spring выполнить метод в транзакции: перед вызовом открыть её, после успешного завершения закоммитить, а при исключении откатить. Ставится на метод или на класс (тогда действует на все его public-методы).
>
> **Как работает:** через **прокси (AOP)**. Spring оборачивает бин в прокси-объект, который перехватывает вызов, открывает транзакцию, вызывает настоящий метод и затем делает commit или rollback.
>
> **Когда происходит откат:**
> - по умолчанию — только при **RuntimeException** и **Error**
> - при **checked-исключениях** (например, `IOException`) транзакция **коммитится**
> - поменять это можно через `rollbackFor = Exception.class` или `noRollbackFor`
>
> **Основные параметры:**
> - **propagation** — что делать, если транзакция уже есть:
>   - `REQUIRED` (по умолчанию) — присоединиться к существующей или создать новую
>   - `REQUIRES_NEW` — приостановить текущую и открыть отдельную. Например, для записи аудита, который должен сохраниться, даже если основная операция откатилась
>   - также есть `SUPPORTS`, `MANDATORY`, `NEVER`, `NOT_SUPPORTED`, `NESTED`
> - **isolation** — уровень изоляции (`READ_COMMITTED`, `REPEATABLE_READ`, `SERIALIZABLE`). По умолчанию берётся уровень базы
> - **readOnly = true** — для методов только на чтение. Hibernate отключает dirty checking, это экономит память и время
> - **timeout** — максимальное время выполнения транзакции в секундах
>
> **Частые ошибки:**
> - **Self-invocation** — вызов транзакционного метода из другого метода того же класса (`this.method()`) идёт мимо прокси, и `@Transactional` **не срабатывает**. Решение — вынести метод в другой бин
> - **private-методы** — прокси их не перехватывает, аннотация игнорируется
> - **Поймали исключение внутри метода** и не пробросили — прокси не узнает об ошибке и сделает commit
> - **Не та аннотация** — нужна `org.springframework.transaction.annotation.Transactional`, а не `jakarta.transaction.Transactional`, у которой меньше возможностей
>
> **Где ставить:** обычно на уровне **сервисов**, а не контроллеров и не репозиториев — транзакция должна охватывать всю бизнес-операцию целиком.

> [!question]- 4.1. Что такое self-invocation и почему из-за него не работает @Transactional?
> Self-invocation (самовызов) — это когда метод бина вызывает **другой метод того же бина** через `this`. Такой вызов идёт **мимо прокси**, поэтому аннотации на вызываемом методе (`@Transactional`, `@Async`, `@Cacheable`) **не срабатывают**.
>
> **Почему так:** Spring кладёт в контекст не сам бин, а **прокси** над ним. Прокси перехватывает только вызовы, которые приходят **снаружи**: из контроллера, из другого сервиса. Когда внутри настоящего объекта вызывается `this.method()`, `this` — это уже сам объект, а не прокси, и перехватить вызов некому.
> ```
> Controller → [Прокси OrderService] → OrderService.createOrder()
>                                              ↓
>                                      this.saveAudit()   ← мимо прокси, аннотация игнорируется
> ```
>
> **Пример:**
> ```java
> @Service
> public class OrderService {
>
>     @Transactional
>     public void createOrder(Order order) {
>         orderRepository.save(order);
>         saveAudit(order);   // то же самое, что this.saveAudit(order)
>         throw new RuntimeException("ошибка");
>     }
>
>     @Transactional(propagation = Propagation.REQUIRES_NEW)
>     public void saveAudit(Order order) {
>         auditRepository.save(new Audit(order));
>     }
> }
> ```
> Ожидание: аудит сохранится в **отдельной** транзакции, даже если заказ откатится.
> Реальность: `REQUIRES_NEW` игнорируется, аудит выполняется **в той же** транзакции и **откатывается вместе с заказом**.
>
> Обратная ситуация тоже частая: у метода без `@Transactional` внутри вызывается `this.transactionalMethod()` — транзакция **вообще не откроется**.
>
> **Как решить:**
> - **вынести метод в отдельный бин** (например, `AuditService`) и внедрить его — вызов пойдёт через прокси. Это основной и самый чистый способ
> ```java
> @Service
> @RequiredArgsConstructor
> public class OrderService {
>     private final AuditService auditService;
>
>     @Transactional
>     public void createOrder(Order order) {
>         orderRepository.save(order);
>         auditService.saveAudit(order);   // через прокси — REQUIRES_NEW работает
>     }
> }
> ```
> - **внедрить самого себя** через `@Lazy` и вызывать `self.saveAudit()` — работает, но выглядит как костыль
> - **TransactionTemplate** — управлять транзакцией программно, без аннотации
> - **AspectJ weaving** вместо прокси — меняет сам байткод, поэтому самовызов тоже перехватывается. Используется редко, сложнее в настройке
>
> **Связанные ограничения прокси:** по той же причине аннотации не работают на **private**-методах и на **final**-методах/классах — прокси не может их перехватить.
>
> **Как коротко ответить на собесе:** «@Transactional работает через прокси. При вызове this.method() внутри класса прокси обходится, поэтому аннотация не срабатывает. Решение — вынести метод в отдельный бин».

> [!question]- 5. Что такое dirty checking?
> Dirty checking — механизм Hibernate, который **сам находит изменённые сущности и сохраняет изменения в базу**, без явного вызова `save()`.
>
> **Как работает:**
> - когда сущность загружается в рамках транзакции, она попадает в **persistence context**, и Hibernate сохраняет **снимок (snapshot)** её исходного состояния
> - перед коммитом (при **flush**) Hibernate сравнивает текущие значения полей каждой сущности со снимком
> - если что-то изменилось, сущность считается «грязной» (dirty), и Hibernate сам генерирует UPDATE
>
> **Пример:**
> ```java
> @Transactional
> public void changeEmail(Long id, String email) {
>     User user = userRepository.findById(id).orElseThrow();
>     user.setEmail(email);
>     // save() не нужен — UPDATE выполнится при коммите
> }
> ```
>
> **Важные условия:**
> - работает только для **managed**-сущностей — загруженных в текущей транзакции. Если сущность пришла извне (detached), например из DTO, изменения сами не сохранятся — нужен `merge()` / `save()`
> - работает только **внутри транзакции**
>
> **Минусы:**
> - **накладные расходы** — Hibernate хранит копию каждой загруженной сущности и сравнивает все поля. При загрузке тысяч записей это память и процессорное время
> - **неявность** — можно случайно поменять поле у сущности (например, для отображения), и изменение улетит в базу
>
> **Как снизить расходы:** для методов только на чтение ставить `@Transactional(readOnly = true)` — Hibernate не делает снимки и не проверяет изменения. Для чтения больших объёмов данных также подходят **проекции (DTO)**, которые вообще не попадают в persistence context.

> [!question]- 6. Что такое прокси?
> Прокси — это объект-обёртка, который **подменяет настоящий объект** и перехватывает вызовы его методов. Он может выполнить дополнительную логику до и после вызова, а саму работу передаёт оригиналу. Это паттерн проектирования **Proxy**.
>
> **Как это использует Spring:** когда на бине есть `@Transactional`, `@Async`, `@Cacheable` или своё AOP-правило, Spring кладёт в контекст **не сам бин, а прокси над ним**. При внедрении зависимости ты получаешь прокси.
> ```
> Controller → [Прокси UserService] → настоящий UserService
>                 ↓
>      открыть транзакцию → вызвать метод → commit / rollback
> ```
>
> **Два способа создания прокси:**
> - **JDK Dynamic Proxy** — создаёт объект, реализующий **те же интерфейсы**, что и бин. Работает только если у класса есть интерфейс
> - **CGLIB** — создаёт **подкласс** бина и переопределяет его методы. Работает и без интерфейсов. В Spring Boot используется **по умолчанию**
>
> **Ограничения:**
> - **self-invocation** — вызов `this.method()` внутри класса идёт напрямую в оригинал, минуя прокси, поэтому `@Transactional` и другие аннотации не срабатывают
> - **private-методы** — прокси их не перехватывает
> - **final-классы и final-методы** — CGLIB не может их переопределить, значит, и перехватить
>
> **Прокси в Hibernate:** ленивые связи (`LAZY`) тоже работают через прокси. Вместо реального объекта Hibernate подставляет заглушку, которая при первом обращении к данным идёт в базу. Если в этот момент сессия уже закрыта, получаем `LazyInitializationException`.

> [!question]- 7. Какие задачи решает Spring Boot и зачем он нужен?
> Spring Boot — надстройка над Spring Framework, которая убирает ручную настройку и позволяет быстро запустить готовое к работе приложение. Сам Spring даёт DI, транзакции, веб, работу с БД, но раньше всё это нужно было долго конфигурировать вручную (XML или Java-конфиги, подбор версий библиотек, настройка сервера).
>
> **Какие задачи решает:**
>
> - **Автоконфигурация** — Spring Boot смотрит, какие библиотеки есть в classpath, и сам создаёт нужные бины. Добавил драйвер Postgres и `spring-boot-starter-data-jpa` — он сам настроит `DataSource`, `EntityManager`, транзакции. Работает через `@Conditional`-аннотации: бин создаётся, только если выполнены условия (есть класс, нет своего бина и т.д.)
>
> - **Стартеры** — готовые наборы зависимостей под задачу: `spring-boot-starter-web`, `-data-jpa`, `-security`, `-test`. Одна зависимость вместо десятка, и **версии всех библиотек уже согласованы** между собой — не нужно вручную искать совместимые
>
> - **Встроенный сервер** — Tomcat (или Jetty, Undertow) уже внутри. Приложение собирается в один **исполняемый jar** и запускается через `java -jar`, без установки и настройки отдельного сервера. Это удобно для Docker и микросервисов
>
> - **Внешняя конфигурация** — все настройки в `application.yml` / `application.properties`, можно переопределять через переменные окружения. Есть **профили** (`dev`, `prod`, `test`) для разных окружений
>
> - **Actuator** — готовые эндпоинты для продакшена: health check, метрики, информация о приложении. Используется для мониторинга и Kubernetes
>
> **Как ускоряет разработку:**
> - проект создаётся за минуту через Spring Initializr и сразу запускается
> - разумные настройки по умолчанию (**convention over configuration**) — настраиваешь только то, что отличается от стандарта
> - меньше шаблонного кода, больше времени на бизнес-логику
>
> **Главная точка входа** — `@SpringBootApplication`, которая объединяет три аннотации:
> - `@Configuration` — класс конфигурации
> - `@EnableAutoConfiguration` — включает автоконфигурацию
> - `@ComponentScan` — ищет бины в текущем пакете и вложенных

> [!question]- 8. Что такое профиль в Spring?
> Профиль — это **именованный набор настроек и бинов для конкретного окружения**: `dev`, `test`, `prod` и т.д. Один и тот же код запускается в разных окружениях, а меняется только конфигурация: какая база, какие URL, какие бины создавать.
>
> **Зачем нужен:**
> - локально работаем с H2 или локальным Postgres, на проде — с реальной базой
> - в тестах подменяем внешние сервисы заглушками (mock платёжного шлюза, отправки SMS)
> - на dev включаем подробные логи и Swagger, на prod выключаем
>
> **1. Профильные файлы конфигурации:**
> - `application.yml` — общие настройки, загружаются **всегда**
> - `application-dev.yml`, `application-prod.yml` — настройки профиля, загружаются поверх общих и **переопределяют** совпадающие значения
>
> ```yaml
> # application-dev.yml
> spring:
>   datasource:
>     url: jdbc:postgresql://localhost:5432/shop_dev
> logging:
>   level:
>     root: DEBUG
> ```
>
> **2. Бины под профиль — `@Profile`:**
> ```java
> @Service
> @Profile("prod")
> public class SmsGatewayNotifier implements Notifier { ... }
>
> @Service
> @Profile("!prod")   // все профили, кроме prod
> public class ConsoleNotifier implements Notifier { ... }
> ```
> Бин создаётся, **только если указанный профиль активен**. Можно ставить на `@Component`, `@Configuration` и `@Bean`-методы. Поддерживаются выражения: `!prod`, `dev | test`, `prod & cloud`.
>
> **Как активировать профиль:**
> - в `application.yml`: `spring.profiles.active: dev`
> - переменная окружения: `SPRING_PROFILES_ACTIVE=prod` — самый частый вариант в Docker и Kubernetes
> - аргумент запуска: `java -jar app.jar --spring.profiles.active=prod`
> - JVM-параметр: `-Dspring.profiles.active=prod`
> - в тестах: `@ActiveProfiles("test")`
>
> Можно активировать **несколько профилей сразу**: `dev,kafka`. Если ни один не указан, работает профиль `default`.
>
> **Группы профилей** (Spring Boot 2.4+) — один профиль включает несколько:
> ```yaml
> spring:
>   profiles:
>     group:
>       prod: prod-db, prod-monitoring
> ```
>
> **Важно:**
> - пароли и секреты **не хранят** в `application-prod.yml` в репозитории. Их передают через переменные окружения или хранилища секретов (Vault, Kubernetes Secrets)
> - профили меняют только конфигурацию. Логика кода должна быть одинаковой, иначе на проде запустится не то, что тестировали

> [!question]- 9. Какие есть способы отправить HTTP-запрос из Java из одного микросервиса в другой?
> Способы делятся на **низкоуровневые клиенты из Java** и **удобные клиенты из Spring**. На практике в Spring-проектах используют Spring-клиенты, чаще всего **OpenFeign**, **RestClient** или **WebClient**.
>
> **Чистая Java и библиотеки:**
> - **`HttpURLConnection`** — самый старый, есть в JDK с первых версий. Многословный и неудобный, сейчас почти не используется
> - **`java.net.http.HttpClient`** (Java 11+) — современный клиент из JDK, поддерживает HTTP/2, синхронные и асинхронные (`CompletableFuture`) запросы
> - **Apache HttpClient, OkHttp** — сторонние библиотеки, часто работают «под капотом» Spring-клиентов (пул соединений, тонкая настройка)
>
> **Spring-клиенты:**
>
> **1. `RestTemplate`** — классический синхронный, блокирующий клиент:
> ```java
> OrderDto order = restTemplate.getForObject(
>         "http://order-service/orders/{id}", OrderDto.class, id);
> ```
> Работает, но сейчас в **режиме поддержки**: новых возможностей не добавляют. Для нового кода Spring советует `RestClient` или `WebClient`.
>
> **2. `WebClient`** (Spring WebFlux) — **неблокирующий, реактивный**, возвращает `Mono` / `Flux`:
> ```java
> Mono<OrderDto> order = webClient.get()
>         .uri("/orders/{id}", id)
>         .retrieve()
>         .bodyToMono(OrderDto.class);
> ```
> Хорош для большой нагрузки и параллельных вызовов. Можно использовать и в обычном MVC-приложении (через `.block()`), но тогда теряется смысл реактивности.
>
> **3. `RestClient`** (Spring 6.1 / Boot 3.2+) — синхронный клиент с **fluent-API, как у WebClient**, но без реактивщины. Современная замена RestTemplate:
> ```java
> OrderDto order = restClient.get()
>         .uri("/orders/{id}", id)
>         .retrieve()
>         .body(OrderDto.class);
> ```
>
> **4. OpenFeign** (Spring Cloud) — **декларативный** клиент. Пишешь только интерфейс, реализацию Spring генерирует сам:
> ```java
> @FeignClient(name = "order-service")
> public interface OrderClient {
>     @GetMapping("/orders/{id}")
>     OrderDto getOrder(@PathVariable Long id);
> }
> ```
> Вызов выглядит как обычный метод: `orderClient.getOrder(id)`. Из коробки интегрируется с service discovery (Eureka), балансировкой и Resilience4j. Очень популярен в микросервисах.
>
> **5. HTTP Interface — `@HttpExchange`** (Spring 6+) — встроенный в Spring аналог Feign: тоже интерфейс с аннотациями (`@GetExchange`, `@PostExchange`), а работает поверх RestClient или WebClient. Не нужна зависимость от Spring Cloud.
>
> **На что обязательно обратить внимание при вызовах между сервисами:**
> - **таймауты** (connect и read) — без них один медленный сервис «подвешивает» потоки вызывающего
> - **retry** — повтор при временных ошибках, но только для идемпотентных запросов
> - **circuit breaker** (Resilience4j) — если сервис падает, перестаём его дёргать и отдаём fallback, чтобы не было каскадного отказа
> - **service discovery и балансировка** — адрес сервиса берётся по имени (Eureka, Consul, DNS в Kubernetes), а не захардкоженным IP
> - **проброс заголовков** — токен авторизации, trace id для распределённой трассировки
>
> **Альтернатива HTTP:** если ответ не нужен сразу, сервисы общаются **асинхронно через брокер** (Kafka, RabbitMQ). Для быстрого внутреннего синхронного общения используют ещё **gRPC**.

> [!question]- 10. Что такое реактивное программирование и чем оно отличается от асинхронного?
> Реактивное программирование — это подход, при котором код работает с **потоками данных и событий**, которые приходят со временем, и **реагирует** на них по мере поступления. Обработка **неблокирующая**: поток не ждёт ответа от БД или другого сервиса, а освобождается и берёт другую работу. Когда результат готов, обработка продолжается.
>
> **Проблема обычного (блокирующего) подхода:**
> В Spring MVC на каждый запрос выделяется поток. Если сервис ждёт ответ от другого сервиса 2 секунды, поток всё это время просто стоит. 1000 одновременных запросов — 1000 потоков, а потоки дорогие (память, переключение контекста).
>
> **Реактивный подход:** небольшое число потоков (примерно по числу ядер) обслуживает тысячи запросов, потому что никто не простаивает в ожидании.
>
> **В Spring:** модуль **WebFlux** + библиотека **Project Reactor**. Основные типы:
> - **`Mono<T>`** — 0 или 1 элемент (один заказ)
> - **`Flux<T>`** — поток из 0..N элементов (список заказов, события, стриминг)
>
> ```java
> public Mono<OrderDto> getOrderWithUser(Long id) {
>     return orderRepository.findById(id)
>             .flatMap(order -> userClient.getUser(order.getUserId())
>                     .map(user -> new OrderDto(order, user)));
> }
> ```
> **Ленивость:** пока на `Mono` / `Flux` никто не подписался (`subscribe`), ничего не выполняется. В WebFlux подписывается сам фреймворк.
>
> **Backpressure** — потребитель может сказать источнику «присылай медленнее», чтобы его не завалило данными.
>
> **Чем отличается от асинхронного программирования:**
> Асинхронность — **общая идея**: запустить задачу и не ждать её на месте. Реактивность — **частный случай асинхронности** со своими дополнительными свойствами. Любой реактивный код асинхронный, но не любой асинхронный код реактивный.
>
> | | Асинхронное | Реактивное |
> |---|---|---|
> | Инструменты в Java | `CompletableFuture`, `@Async`, `ExecutorService` | Reactor (`Mono`/`Flux`), RxJava |
> | Результат | обычно **один** результат в будущем | **поток** из многих элементов во времени |
> | Блокировка | может быть блокирующим, просто в другом потоке | неблокирующее по всей цепочке |
> | Backpressure | нет | есть |
> | Запуск | сразу при вызове | лениво, при подписке |
>
> **Важный нюанс про `@Async`:** метод выполняется в другом потоке, но если внутри он ждёт БД или HTTP, то **блокирует уже этот поток**. Проблема ожидания просто переносится в другой пул. Реактивный подход решает её по-настоящему: во время ожидания поток вообще не занят.
>
> **Минусы реактивщины:**
> - код сложнее писать и читать, стектрейсы запутанные, отладка тяжелее
> - вся цепочка должна быть неблокирующей. Один вызов JDBC/JPA внутри «убивает» выгоду. Для БД нужен реактивный драйвер **R2DBC**
> - для обычного CRUD с умеренной нагрузкой выигрыша почти нет
>
> **Когда использовать:** высокая нагрузка с большим количеством I/O (много вызовов других сервисов), стриминг данных, API gateway (Spring Cloud Gateway построен на WebFlux).
>
> **Альтернатива — виртуальные потоки** (Java 21, Project Loom). Они очень лёгкие, поэтому можно писать обычный блокирующий код в Spring MVC и всё равно держать тысячи запросов. Многие проекты теперь выбирают этот вариант вместо WebFlux, потому что код остаётся простым.

> [!question]- 11. Что такое Inversion of Control и Dependency Injection?
> **Inversion of Control (IoC, инверсия управления)** — это **принцип**: управление созданием объектов и их жизненным циклом передаётся **от нашего кода фреймворку** (контейнеру). Не мы создаём объекты и вызываем всё вручную, а фреймворк создаёт их и вызывает наш код, когда нужно. Принцип Голливуда: «не звоните нам, мы сами вам позвоним».
>
> **Dependency Injection (DI, внедрение зависимостей)** — это **конкретный способ реализовать IoC**: объект **не создаёт свои зависимости сам**, а получает их **извне** — через конструктор, сеттер или поле.
>
> Коротко: **IoC — идея, DI — её реализация**.
>
> **Без DI — объект сам создаёт зависимости:**
> ```java
> public class OrderService {
>     private final PaymentClient paymentClient = new KaspiPaymentClient();
>     private final OrderRepository repository = new JdbcOrderRepository();
> }
> ```
> Проблемы:
> - `OrderService` **жёстко привязан** к конкретным классам. Чтобы сменить платёжку, нужно менять его код
> - **сложно тестировать** — нельзя подставить мок вместо настоящего клиента
> - сервис сам должен знать, **как создать** зависимости (URL, настройки, пул соединений)
>
> **С DI — зависимости передаются снаружи:**
> ```java
> @Service
> public class OrderService {
>     private final PaymentClient paymentClient;     // интерфейс, а не конкретный класс
>     private final OrderRepository repository;
>
>     public OrderService(PaymentClient paymentClient, OrderRepository repository) {
>         this.paymentClient = paymentClient;
>         this.repository = repository;
>     }
> }
> ```
> Теперь `OrderService` только **использует** зависимости. Какую реализацию подставить, решает Spring. В тесте можно просто передать моки: `new OrderService(mockClient, mockRepo)`.
>
> **Как это работает в Spring:**
> - **IoC-контейнер** — `ApplicationContext` (базовый интерфейс — `BeanFactory`). Он создаёт объекты, связывает их между собой и управляет их жизненным циклом
> - объекты, которыми управляет контейнер, называются **бинами**
> - бины объявляются аннотациями `@Component`, `@Service`, `@Repository`, `@Controller` (находятся через component scan) или методами с `@Bean` в классе `@Configuration`
> - при старте контейнер строит граф зависимостей, создаёт бины в нужном порядке и внедряет их друг в друга
>
> **Способы внедрения:**
> - **через конструктор** — **рекомендуемый**. Если конструктор один, `@Autowired` писать не нужно (с Spring 4.3). Плюсы: поля можно сделать `final`, объект не создастся без обязательных зависимостей, легко тестировать без Spring, циклические зависимости обнаруживаются сразу при старте. С Lombok — `@RequiredArgsConstructor`
> - **через сеттер** — для **необязательных** зависимостей, которые можно поменять после создания
> - **через поле** (`@Autowired` на поле) — **не рекомендуется**: поле нельзя сделать `final`, зависимости скрыты, без Spring (в unit-тесте) их не подставить без рефлексии
>
> **Если реализаций интерфейса несколько:**
> - `@Primary` — какая реализация будет по умолчанию
> - `@Qualifier("kaspiPaymentClient")` — явно указать нужный бин
> - можно внедрить **все** реализации сразу: `List<PaymentClient>` или `Map<String, PaymentClient>` (ключ — имя бина)
>
> **Отличие от Dependency Inversion Principle (буква D в SOLID):**
> - **DIP** — принцип проектирования: модули должны зависеть от **абстракций** (интерфейсов), а не от конкретных классов
> - **DI** — механизм, **кто и как передаёт** зависимость
> - они хорошо работают вместе: класс зависит от интерфейса (DIP), а конкретную реализацию ему передаёт контейнер (DI)
>
> **Нюансы:**
> - **циклические зависимости** (A зависит от B, B от A) — со Spring Boot 2.6 по умолчанию запрещены, приложение не стартует. Обычно это признак плохого дизайна: нужно вынести общую логику в третий бин
> - IoC — это не только DI. Другие примеры инверсии управления: фреймворк сам вызывает наши методы-обработчики (`@GetMapping`, `@EventListener`, `@Scheduled`), шаблонный метод
> - альтернатива DI — **Service Locator**, когда объект сам просит зависимость у реестра (`context.getBean(...)`). Считается хуже: зависимости скрыты внутри кода и класс привязан к контейнеру

> [!question]- 11.1. Есть заказ и несколько способов оплаты (Kaspi, Halyk, наличные), каждый со своей реализацией. Как выбрать нужную оплату без if-else?
> Решение через if-else работает, но лучше использовать паттерн **Стратегия (Strategy)**: общий интерфейс для всех способов оплаты, каждая оплата — отдельная реализация-бин, а сервис выбирает нужную по типу. В Spring для этого удобно **внедрить сразу все реализации** интерфейса.
>
> **Почему if-else — плохой вариант:**
> ```java
> if (type == PaymentType.KASPI) kaspiPayment.pay(order);
> else if (type == PaymentType.HALYK) halykPayment.pay(order);
> else if (type == PaymentType.CASH) cashPayment.pay(order);
> ```
> - при каждом новом способе оплаты (Freedom, Apple Pay) нужно **менять код сервиса** и дописывать ветку
> - сервис зависит от **всех** конкретных платёжек и разрастается
> - нарушается **Open/Closed principle** (буква O в SOLID): код должен быть открыт для расширения, но закрыт для изменения
>
> **Решение через Стратегию:**
>
> **1. Общий интерфейс:**
> ```java
> public interface PaymentStrategy {
>     PaymentType getType();
>     void pay(Order order);
> }
> ```
>
> **2. Каждый способ оплаты — отдельный бин:**
> ```java
> @Component
> public class KaspiPayment implements PaymentStrategy {
>     public PaymentType getType() { return PaymentType.KASPI; }
>     public void pay(Order order) { /* вызов API Kaspi */ }
> }
>
> @Component
> public class HalykPayment implements PaymentStrategy { ... }
>
> @Component
> public class CashPayment implements PaymentStrategy { ... }
> ```
>
> **3. Сервис получает все реализации и выбирает по типу:**
> ```java
> @Service
> public class OrderService {
>     private final Map<PaymentType, PaymentStrategy> strategies;
>
>     public OrderService(List<PaymentStrategy> strategyList) {   // Spring передаст все реализации
>         this.strategies = strategyList.stream()
>             .collect(Collectors.toMap(PaymentStrategy::getType, Function.identity()));
>     }
>
>     public void checkout(Order order, PaymentType type) {
>         PaymentStrategy strategy = strategies.get(type);
>         if (strategy == null) {
>             throw new IllegalArgumentException("Неподдерживаемый способ оплаты: " + type);
>         }
>         strategy.pay(order);
>     }
> }
> ```
> Вариант попроще: внедрить `Map<String, PaymentStrategy>` — Spring сам соберёт мапу, где ключ — **имя бина** (`kaspiPayment`, `halykPayment`). Но ключ-строка менее надёжен, чем enum.
>
> **Что это даёт:**
> - новый способ оплаты = **новый класс** с `@Component`. `OrderService` не меняется
> - логика каждой платёжки **изолирована** в своём классе
> - легко тестировать: каждую стратегию отдельно, сервис — с моками
> - по сути это **полиморфизм**: сервис работает через общий интерфейс и не знает, какая реализация пришла
>
> **Фабрика (Factory) как вариант:**
> Выбор стратегии можно вынести в отдельный класс `PaymentStrategyFactory` с методом `get(PaymentType type)`. Внутри — та же мапа. Плюс: сервис не занимается выбором, а несколько сервисов могут переиспользовать фабрику.
>
> **Нюансы:**
> - если две реализации вернут одинаковый `getType()`, `Collectors.toMap` выбросит `IllegalStateException` при старте — это хорошо, ошибка конфигурации видна сразу
> - обязательно обрабатывать **неизвестный тип** (как в примере выше), чтобы не получить `NullPointerException`
> - для 2–3 вариантов, которые никогда не будут меняться, `switch` по enum тоже допустим — не нужно усложнять без причины. Стратегия выигрывает, когда способов много или они добавляются
