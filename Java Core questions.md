> [!question]- 1. Что такое виртуальные потоки?
> Виртуальные потоки (virtual threads) — это **лёгкие потоки, которыми управляет JVM, а не операционная система**. Появились в **Java 21** (проект **Loom**). Их можно создавать **миллионами**, и они позволяют писать обычный блокирующий код, который при этом держит огромную нагрузку.
>
> **Проблема обычных (платформенных) потоков:**
> Обычный `Thread` в Java — это обёртка над **потоком ОС**, один к одному. Он дорогой:
> - занимает около **1 МБ памяти** под стек
> - создание и переключение между потоками делает ОС, это медленно
> - на машине реально держать **несколько тысяч** потоков, не больше
>
> В модели «поток на запрос» (Spring MVC, Tomcat) поток большую часть времени **ждёт** ответа от БД или другого сервиса. Потоки заканчиваются раньше, чем процессор успевает загрузиться.
>
> **Как работают виртуальные потоки:**
> - JVM запускает виртуальные потоки поверх небольшого пула обычных потоков — **carrier threads** (их примерно столько, сколько ядер)
> - когда виртуальный поток делает **блокирующую операцию** (запрос в БД, HTTP, `sleep`), JVM **отсоединяет** его от carrier-потока и сохраняет его стек в куче
> - carrier-поток сразу берёт другой виртуальный поток
> - когда ответ пришёл, виртуальный поток снова садится на любой свободный carrier и продолжает работу с того же места
>
> Получается, что **код выглядит блокирующим, а работает как неблокирующий**. Стек небольшой и растёт по необходимости, поэтому один виртуальный поток занимает **килобайты**, а не мегабайт.
>
> **Как создать:**
> ```java
> // один поток
> Thread.ofVirtual().start(() -> processPayment(paymentId));
>
> // executor: новый виртуальный поток на каждую задачу
> try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
>     executor.submit(() -> fetchUserProfile(userId));
>     executor.submit(() -> fetchUserOrders(userId));
> }
> ```
>
> **В Spring Boot** (3.2+) включается одной настройкой:
> ```yaml
> spring:
>   threads:
>     virtual:
>       enabled: true
> ```
> После этого Tomcat обрабатывает каждый запрос в виртуальном потоке. Код контроллеров и сервисов менять не нужно.
>
> **Сравнение с реактивщиной (WebFlux):** обе технологии решают одну задачу — не держать поток занятым во время ожидания I/O. Но с виртуальными потоками код остаётся **обычным и простым**: читаемые стектрейсы, нормальная отладка, работают JDBC и JPA. Поэтому многие выбирают MVC + виртуальные потоки вместо WebFlux.
>
> **Ограничения и нюансы:**
> - **не ускоряют вычисления.** Помогают только при большом количестве **ожидания I/O**. Для CPU-задач (математика, обработка картинок) выигрыша нет
> - **пиннинг (pinning)** — в некоторых случаях виртуальный поток «прилипает» к carrier и блокирует его. В Java 21 это происходит при блокировке внутри `synchronized` и при нативных вызовах. Рекомендация для Java 21 — использовать `ReentrantLock` вместо `synchronized`. В **Java 24** проблему с `synchronized` исправили
> - **не нужно складывать их в пул.** Они дешёвые: создаём новый поток на каждую задачу и выбрасываем
> - **осторожно с `ThreadLocal`.** При миллионе потоков у каждого своя копия, памяти может уйти много. Есть альтернатива — `ScopedValue`
> - **внешние ресурсы не бесконечны.** Потоков может быть миллион, а соединений с БД в пуле, например, 20. Нагрузку всё равно нужно ограничивать (пул соединений, `Semaphore`)

> [!question]- 2. В чём заключается контракт equals и hashCode класса Object?
> Контракт — это набор правил, которые должны соблюдать `equals()` и `hashCode()`, чтобы объекты правильно работали в коллекциях на основе хешей (`HashMap`, `HashSet`). Главное правило: **если два объекта равны по `equals`, у них обязан быть одинаковый `hashCode`**.
>
> **По умолчанию в Object:**
> - `equals()` сравнивает **ссылки** (`this == obj`), то есть объект равен только самому себе
> - `hashCode()` возвращает число, обычно связанное с конкретным объектом в памяти, поэтому у разных объектов оно, как правило, разное
>
> **Правила для equals:**
> - **рефлексивность** — `a.equals(a)` всегда `true`
> - **симметричность** — если `a.equals(b)`, то и `b.equals(a)`
> - **транзитивность** — если `a.equals(b)` и `b.equals(c)`, то `a.equals(c)`
> - **консистентность** — повторные вызовы дают один и тот же результат, пока объекты не менялись
> - **сравнение с null** — `a.equals(null)` всегда `false`, без исключения
>
> **Правила для hashCode:**
> - равные по `equals` объекты → **одинаковый** `hashCode`
> - одинаковый `hashCode` **не значит**, что объекты равны. Это коллизия, и она допустима
> - для одного и того же объекта `hashCode` не меняется, пока не меняются поля, участвующие в `equals`
>
> **Почему это важно — как работает HashMap:**
> 1. по `hashCode` ключа вычисляется **бакет** (корзина)
> 2. внутри бакета нужный ключ ищется через `equals`
>
> Если переопределить только `equals`, а `hashCode` оставить из Object, два «равных» объекта попадут в **разные бакеты**:
> ```java
> class Product {
>     String sku;
>     Product(String sku) { this.sku = sku; }
>
>     @Override
>     public boolean equals(Object o) {
>         if (this == o) return true;
>         if (!(o instanceof Product p)) return false;
>         return sku.equals(p.sku);
>     }
>     // hashCode НЕ переопределён
> }
>
> Set<Product> set = new HashSet<>();
> set.add(new Product("A-100"));
> set.contains(new Product("A-100")); // false — ищет в другом бакете
> set.add(new Product("A-100"));      // добавится дубликат
> ```
>
> **Правильно — переопределять оба метода по одним и тем же полям:**
> ```java
> @Override
> public int hashCode() {
>     return Objects.hash(sku);
> }
> ```
> На практике их генерирует IDE, Lombok (`@EqualsAndHashCode`) или они создаются автоматически в **record**.
>
> **Нюансы:**
> - **изменяемые поля в ключе** — если положить объект в `HashSet`, а потом поменять поле, от которого зависит `hashCode`, объект «потеряется»: он лежит в старом бакете, а ищется в новом. Поэтому ключи лучше делать неизменяемыми
> - **плохой hashCode** (например, всегда `return 1`) контракт не нарушает, но все элементы попадут в один бакет, и поиск станет медленным
> - **JPA-сущности** — не стоит строить `equals/hashCode` по сгенерированному `id`: до сохранения он `null`, после сохранения меняется. Обычно используют бизнес-ключ (email, артикул) или делают `hashCode` константным для класса
> - `instanceof` против `getClass()` в `equals`: `getClass()` строже и не ломает симметричность при наследовании

> [!question]- 2.1. Что вообще такое контракт в программировании?
> Контракт — это **договорённость о поведении метода, класса или интерфейса**: что он принимает, что гарантирует вернуть и каким правилам подчиняется. Компилятор его **не проверяет**, он описан в документации (Javadoc), а соблюдать его обязан разработчик.
>
> **Из чего обычно состоит контракт:**
> - **предусловия** — что должно быть верно до вызова (например, аргумент не `null`, индекс в пределах размера)
> - **постусловия** — что метод гарантирует после выполнения (например, `list.add(x)` → размер увеличился на 1)
> - **инварианты** — что всегда верно для объекта (например, баланс счёта не отрицательный)
> - **поведение при ошибках** — какие исключения и в каких случаях выбрасываются
>
> **Отличие от сигнатуры:** сигнатура `boolean equals(Object o)` говорит только, *что* метод принимает и возвращает. Контракт говорит, *как* он должен себя вести: симметрично, транзитивно, `false` для `null` и т.д. Код с неправильным `equals` скомпилируется, но контракт будет нарушен.
>
> **Зачем нужен:** другой код **полагается** на контракт. `HashMap`, `HashSet`, `Collections.sort` написаны с расчётом, что `equals`, `hashCode`, `compareTo` ведут себя по правилам. Если контракт нарушен, ошибки не будет на этапе компиляции, но коллекции начнут работать неправильно: «терять» элементы, хранить дубликаты, сортировать непредсказуемо.
>
> **Примеры контрактов в Java:**
> - `equals` / `hashCode` — равные объекты → одинаковый хеш
> - `Comparable.compareTo` — согласованность с `equals`, транзитивность, `sgn(a.compareTo(b)) == -sgn(b.compareTo(a))`
> - `Iterator` — `next()` бросает `NoSuchElementException`, если элементов больше нет
> - `AutoCloseable.close()` — освобождает ресурс
>
> **Связь с ООП:** принцип подстановки Лисков (буква **L** в SOLID) по сути говорит, что наследник **не должен нарушать контракт** родителя: не усиливать предусловия и не ослаблять постусловия. Тогда объект наследника можно подставить везде, где ждут родителя.

> [!question]- 2.2. Как устроен бакет в HashMap и как HashMap работает внутри?
> Внутри `HashMap` — это **массив бакетов** (`Node<K,V>[] table`). Бакет — это одна ячейка массива. В ней лежит либо `null`, либо **связный список** узлов, либо (при большом количестве коллизий) **красно-чёрное дерево**.
>
> **Из чего состоит узел (Node):**
> ```java
> static class Node<K,V> {
>     final int hash;   // закешированный хеш ключа
>     final K key;
>     V value;
>     Node<K,V> next;   // ссылка на следующий узел в том же бакете
> }
> ```
>
> **Основные параметры:**
> - **capacity** (ёмкость) — размер массива, по умолчанию **16**, всегда **степень двойки**
> - **load factor** — коэффициент заполнения, по умолчанию **0.75**
> - **threshold** — порог расширения = capacity × load factor (16 × 0.75 = **12** элементов)
> - сам массив создаётся **лениво** — при первом `put`, а не в конструкторе
>
> **Как работает put(key, value):**
> 1. считается `key.hashCode()`, затем он «перемешивается»: `hash = h ^ (h >>> 16)` — старшие биты смешиваются с младшими, чтобы распределение было ровнее
> 2. вычисляется индекс бакета: `index = (n - 1) & hash` (n — размер массива). Это то же самое, что `hash % n`, но быстрее, и работает именно потому, что n — степень двойки
> 3. если бакет пустой — кладём туда новый узел
> 4. если не пустой — идём по узлам и для каждого сравниваем: сначала `hash`, потом `key == k || key.equals(k)`
>    - нашли такой ключ → **заменяем value** (старое значение возвращается из `put`)
>    - не нашли → добавляем новый узел **в конец списка** (с Java 8; в Java 7 вставляли в начало)
> 5. если размер стал больше threshold → **resize**
>
> **Как работает get(key):** тот же хеш → тот же индекс бакета → проход по узлам с проверкой `hash` и `equals`. Поэтому для ключей так важен контракт `equals/hashCode`.
>
> **Коллизии и превращение в дерево (Java 8+):**
> - **коллизия** — разные ключи попали в один бакет
> - если в одном бакете набралось **8 узлов** (`TREEIFY_THRESHOLD`), а размер массива **≥ 64** (`MIN_TREEIFY_CAPACITY`), список превращается в **красно-чёрное дерево** (`TreeNode`). Поиск в бакете становится **O(log n)** вместо O(n)
> - если массив меньше 64, вместо дерева HashMap просто делает **resize** — обычно это лучше разносит элементы
> - если после удалений в дереве осталось **6 узлов и меньше** (`UNTREEIFY_THRESHOLD`), оно снова превращается в список
>
> **Resize (расширение):**
> - массив **увеличивается в 2 раза**, все элементы перераспределяются
> - благодаря степени двойки хеш заново не считается: каждый элемент либо остаётся на **том же индексе**, либо переезжает на **индекс + старая ёмкость** — это определяется одним битом хеша
> - resize — дорогая операция O(n). Если заранее известно количество элементов, лучше задать начальную ёмкость: `new HashMap<>(expectedSize / 0.75 + 1)` или в Java 19+ `HashMap.newHashMap(expectedSize)`
>
> **Сложность:**
> - в среднем `get` / `put` / `remove` — **O(1)**
> - в худшем случае (все ключи в одном бакете) — O(n) для списка, **O(log n)** после превращения в дерево
>
> **Нюансы:**
> - **ключ `null`** разрешён (один), его хеш считается равным 0, поэтому он всегда лежит в бакете 0
> - **порядок не гарантирован** и может поменяться после resize. Нужен порядок вставки — `LinkedHashMap`, сортировка — `TreeMap`
> - **не потокобезопасен.** При одновременной записи из нескольких потоков можно потерять данные. Для многопоточности — `ConcurrentHashMap`
> - **изменяемый ключ** — если после `put` поменять поле, от которого зависит `hashCode`, элемент останется в старом бакете и его больше не найти через `get`

> [!question]- 2.3. Как работает метод put в HashMap внутри?
> `put(key, value)` находит бакет по хешу ключа, затем в этом бакете либо **заменяет значение** существующего ключа, либо **добавляет новый узел**. После добавления проверяется, не пора ли расширить массив. Метод возвращает **старое значение** или `null`, если ключа не было.
>
> **Пошагово:**
>
> **1. Считается hash ключа**
> ```java
> hash = (key == null) ? 0 : key.hashCode() ^ (key.hashCode() >>> 16);
> ```
> Берётся `hashCode()` ключа и перемешивается: старшие биты смешиваются с младшими, чтобы ключи равномернее распределялись по бакетам. Для `null`-ключа hash = 0, поэтому он всегда лежит в бакете 0.
>
> **2. Если массив ещё не создан — создаётся**
> Массив бакетов создаётся **лениво**, при первом `put`. По умолчанию размер 16.
>
> **3. Вычисляется индекс бакета**
> ```java
> index = (n - 1) & hash;   // n — размер массива
> ```
> Это быстрый аналог `hash % n`, работает, потому что n — степень двойки. Получаем число от 0 до n-1.
>
> **4. Бакет пустой** → создаётся новый узел `Node(hash, key, value, null)` и кладётся в ячейку. Переходим к шагу 6.
>
> **5. Бакет не пустой** — идём по узлам и ищем такой же ключ. Для каждого узла проверяется:
> ```java
> node.hash == hash && (node.key == key || key.equals(node.key))
> ```
> Сначала сравнивается hash (быстро, отсекает большинство), потом ссылка `==`, и только потом `equals`.
> - **ключ найден** → старое значение **заменяется** новым, метод возвращает старое значение. Размер мапы не меняется, resize не нужен
> - **ключ не найден** → новый узел добавляется **в конец списка** (с Java 8; в Java 7 — в начало)
> - если бакет уже **дерево** (`TreeNode`) → вставка идёт в красно-чёрное дерево
>
> **Превращение в дерево:** если после вставки в списке стало **8 узлов**, вызывается `treeifyBin`. Если размер массива **≥ 64**, список превращается в красно-чёрное дерево. Если меньше — вместо этого делается **resize**.
>
> **6. Увеличивается размер и проверяется порог**
> - `size++` и `modCount++` (счётчик изменений — по нему итератор понимает, что мапу изменили во время обхода, и бросает `ConcurrentModificationException`)
> - если `size > threshold` (capacity × 0.75, по умолчанию 12) → **resize**: массив увеличивается в 2 раза, все элементы перераспределяются
>
> **7. Возвращается результат** — `null`, если ключ новый, или старое значение, если ключ уже был.
>
> **Пример:**
> ```java
> Map<String, Integer> stock = new HashMap<>();
> stock.put("apple", 10);   // вернёт null — ключ новый
> stock.put("apple", 25);   // вернёт 10 — значение заменено
> stock.size();             // 1
> ```
>
> **Нюансы:**
> - из-за того, что `put` возвращает `null` и для нового ключа, и для ключа со значением `null`, по результату нельзя точно понять, был ли ключ. Для этого есть `containsKey`
> - родственные методы: `putIfAbsent` (не перезаписывает существующее), `computeIfAbsent`, `merge`
> - если у ключа плохой `hashCode` (например, всегда одинаковый), все элементы попадут в один бакет, и `put` деградирует до O(n), а после превращения в дерево — до O(log n)
> - `put` **не потокобезопасен**: при одновременной записи из нескольких потоков данные могут потеряться

> [!question]- 2.4. Может ли hashCode ключа зависеть от изменяемого поля и что будет, если это поле поменять?
> Да, технически может: если `hashCode` считается по полю, которое можно изменить (сеттер, не `final`), то после изменения поля **меняется и `hashCode`**. Компилятор этого не запрещает. Но если такой объект уже лежит в `HashMap` как ключ (или в `HashSet`), он **«теряется»**: лежит в старом бакете, а ищется в новом.
>
> **Почему так происходит:**
> - при `put` по старому `hashCode` вычислился бакет, и в узле **закешировался hash**
> - поле поменяли → `hashCode` стал другим
> - при `get` вычисляется **новый** индекс бакета, HashMap идёт туда и ничего не находит. Даже если случайно попадёт в тот же бакет, не совпадёт закешированный hash
>
> **Пример:**
> ```java
> class Seat {
>     private String row;
>     Seat(String row) { this.row = row; }
>     void setRow(String row) { this.row = row; }
>
>     @Override public boolean equals(Object o) {
>         return o instanceof Seat s && row.equals(s.row);
>     }
>     @Override public int hashCode() { return row.hashCode(); }
> }
>
> Map<Seat, String> bookings = new HashMap<>();
> Seat seat = new Seat("A");
> bookings.put(seat, "Ivan");
>
> seat.setRow("B");               // hashCode изменился
>
> bookings.get(seat);             // null — ищет в другом бакете
> bookings.containsKey(seat);     // false
> bookings.remove(seat);          // ничего не удалит
> bookings.size();                // 1 — запись всё ещё внутри
> bookings.put(seat, "Petr");     // добавится ВТОРАЯ запись, size = 2
> ```
>
> **Последствия:**
> - `get`, `containsKey`, `remove` **не находят** элемент
> - запись остаётся внутри мапы — её видно при переборе (`entrySet()`, `keySet()`), но достать по ключу нельзя
> - повторный `put` того же объекта создаёт **дубликат**
> - «потерянные» записи невозможно удалить → **утечка памяти**, если такое происходит постоянно
> - если вернуть полю старое значение, элемент снова начнёт находиться — поведение непредсказуемое и трудно отлаживается
> - ошибки и исключения нет — программа просто молча работает неправильно
>
> **Как избежать:**
> - делать ключи **неизменяемыми**: `String`, `Integer`, `UUID`, `record`, классы с `final`-полями без сеттеров
> - в `equals` / `hashCode` использовать только поля, которые **не меняются** после создания (например, id или бизнес-ключ)
> - если поле всё-таки нужно изменить — сначала **удалить** объект из мапы, изменить, потом **положить заново**
>
> **Где это встречается на практике:**
> - **JPA-сущности** с `hashCode` по `@Id`: до сохранения id = `null`, после `save` он появляется → `hashCode` меняется. Если сущность лежала в `HashSet` (например, в коллекции `@OneToMany`), она там «теряется». Поэтому у сущностей `hashCode` делают по неизменяемому бизнес-ключу или константным для класса
> - та же проблема есть у **TreeMap / TreeSet**: если поменять поле, по которому работает `compareTo`, элемент окажется не на своём месте в дереве

> [!question]- 3. В чём различие ArrayList и LinkedList?
> Оба реализуют интерфейс `List`, но устроены по-разному: **ArrayList** хранит элементы в **массиве**, а **LinkedList** — в **двусвязном списке** узлов. Из-за этого у них разная скорость операций и расход памяти. На практике почти всегда используют **ArrayList**.
>
> **Как устроен ArrayList:**
> - внутри обычный массив `Object[] elementData`
> - начальная ёмкость — **10** (массив создаётся при первом `add`)
> - когда массив заполнен, создаётся новый массив **в 1.5 раза больше**, и элементы копируются туда
> - реализует маркерный интерфейс `RandomAccess` — быстрый доступ по индексу
>
> **Как устроен LinkedList:**
> - каждый элемент лежит в отдельном узле: `Node { item, prev, next }`
> - сам список хранит ссылки на **первый** и **последний** узлы
> - реализует не только `List`, но и `Deque`, поэтому умеет работать как очередь и стек
>
> **Сравнение операций:**
>
> | Операция | ArrayList | LinkedList |
> |---|---|---|
> | `get(index)` | **O(1)** — сразу по индексу массива | **O(n)** — идём по узлам от начала или конца (с ближней стороны) |
> | `add(e)` в конец | **O(1)** амортизированно (иногда O(n) при расширении) | **O(1)** |
> | вставка / удаление в начале | **O(n)** — сдвиг всех элементов | **O(1)** |
> | вставка / удаление в середине | **O(n)** — сдвиг элементов | **O(n)** — сначала нужно дойти до места, сама перестановка ссылок O(1) |
> | память | только массив ссылок | на каждый элемент — объект-узел с двумя доп. ссылками, в разы больше |
>
> **Важный момент про «LinkedList быстрее вставляет в середину»:** это популярный миф. Вставка за O(1) возможна, только если мы **уже стоим** на нужном месте (например, через `ListIterator`). Если вставляем по индексу, LinkedList сначала проходит O(n) узлов, чтобы найти позицию.
>
> **Почему ArrayList почти всегда быстрее на практике:**
> - элементы массива лежат в памяти **подряд**, процессор хорошо кеширует их (**cache locality**). Узлы LinkedList разбросаны по куче, и каждый переход — это промах кеша
> - сдвиг элементов в ArrayList делается через `System.arraycopy` — очень быструю нативную операцию
> - меньше объектов → меньше нагрузка на сборщик мусора
>
> **Когда что использовать:**
> - **ArrayList** — по умолчанию почти в любой ситуации: хранение, перебор, доступ по индексу
> - **LinkedList** — редко: частые вставки и удаления через итератор в процессе обхода
> - нужна **очередь или стек** — лучше `ArrayDeque`, а не LinkedList: он тоже на массиве и быстрее
>
> **Общее у обоих:**
> - допускают дубликаты и `null`
> - сохраняют порядок вставки
> - **не потокобезопасны**. Для многопоточности — `CopyOnWriteArrayList` (много чтений, мало записей) или `Collections.synchronizedList`
> - если заранее известен размер, у ArrayList можно задать ёмкость в конструкторе (`new ArrayList<>(1000)`), чтобы избежать лишних расширений

> [!question]- 4. Расскажите про Map: какие у него есть реализации и чем они отличаются?
> `Map` — это интерфейс для хранения пар **ключ–значение**, где ключи **уникальны**. Важно: `Map` **не наследуется от `Collection`**, это отдельная ветка коллекций. Строго говоря, у интерфейса не «наследники», а **реализации**.
>
> **Иерархия:**
> ```
> Map (I)
> ├── HashMap (C)
> │   └── LinkedHashMap (C)
> ├── Hashtable (C)                   ← устаревший
> ├── ConcurrentMap (I)
> │   └── ConcurrentHashMap (C)
> ├── SortedMap (I)
> │   └── NavigableMap (I)
> │       └── TreeMap (C)
> ├── EnumMap (C)
> ├── WeakHashMap (C)
> └── IdentityHashMap (C)
> ```
>
> **Основные реализации:**
>
> **HashMap** — самая используемая
> - внутри массив бакетов, ключ ищется по `hashCode` и `equals`
> - `get` / `put` в среднем **O(1)**
> - **порядок не гарантирован**
> - разрешает **один `null`-ключ** и `null`-значения
> - не потокобезопасен
>
> **LinkedHashMap** — HashMap + **сохранение порядка**
> - наследуется от HashMap, дополнительно связывает все элементы двусвязным списком
> - по умолчанию хранит **порядок вставки**
> - можно включить **порядок доступа** (`accessOrder = true`): элемент, к которому обратились, переезжает в конец. Вместе с методом `removeEldestEntry` это готовый **LRU-кеш**
> - чуть больше памяти, чем HashMap, скорость та же — O(1)
>
> **TreeMap** — **отсортированная** мапа
> - внутри **красно-чёрное дерево**
> - ключи всегда отсортированы: по естественному порядку (`Comparable`) или по своему `Comparator`
> - операции **O(log n)**
> - ключи сравниваются через `compareTo`, а не через `equals/hashCode`
> - **`null`-ключ нельзя** — будет `NullPointerException`
> - есть удобные навигационные методы: `firstKey()`, `lastKey()`, `floorKey()`, `ceilingKey()`, `headMap()`, `tailMap()`, `subMap()` — например, найти ближайшую дату или все значения в диапазоне
>
> **ConcurrentHashMap** — **потокобезопасная** мапа
> - в Java 8+ блокируется **не вся мапа, а только один бакет** при записи (CAS + `synchronized` на первом узле бакета). Чтение почти всегда без блокировок
> - поэтому много потоков могут одновременно работать с разными бакетами
> - **`null` нельзя** ни в ключах, ни в значениях: иначе `get` вернувший `null` нельзя отличить от «ключа нет», а в многопоточке это критично
> - есть атомарные операции: `putIfAbsent`, `computeIfAbsent`, `merge`
>
> **Hashtable** — **устаревший**
> - потокобезопасен, но все методы `synchronized`, то есть блокируется **вся таблица** целиком — медленно
> - `null` запрещён
> - в новом коде вместо него используют ConcurrentHashMap
>
> **Специализированные:**
> - **EnumMap** — ключи только из одного `enum`. Внутри обычный массив по порядковому номеру константы, очень быстрый и компактный
> - **WeakHashMap** — ключи хранятся через слабые ссылки: если на ключ больше нигде нет ссылок, сборщик мусора может удалить запись. Иногда используют для кешей
> - **IdentityHashMap** — сравнивает ключи по ссылке (`==`), а не через `equals`
> - **`Map.of(...)` / `Map.copyOf(...)`** — неизменяемые мапы (Java 9+), `null` запрещён, порядок не гарантирован
>
> **Сравнение основных:**
>
> | | HashMap | LinkedHashMap | TreeMap | ConcurrentHashMap |
> |---|---|---|---|---|
> | Порядок | нет | вставки / доступа | отсортирован | нет |
> | Скорость | O(1) | O(1) | O(log n) | O(1) |
> | `null`-ключ | да (один) | да (один) | нет | нет |
> | Потокобезопасность | нет | нет | нет | да |
>
> **Как выбирать:**
> - обычный случай → **HashMap**
> - нужен порядок вставки или LRU-кеш → **LinkedHashMap**
> - нужна сортировка ключей или поиск по диапазону → **TreeMap**
> - доступ из нескольких потоков → **ConcurrentHashMap**

> [!question]- 5. Что нужно сделать, чтобы объект стал immutable (неизменяемым)?
> Immutable-объект — это объект, состояние которого **нельзя изменить после создания**. Если нужно «изменить» — создаётся **новый объект**. Примеры из JDK: `String`, `Integer` и другие обёртки, `LocalDate`, `BigDecimal`, `UUID`.
>
> **Правила, как сделать класс неизменяемым:**
> 1. **Класс `final`** — чтобы нельзя было создать наследника, который добавит изменяемое состояние или переопределит методы (альтернатива — `private` конструктор + статический фабричный метод)
> 2. **Все поля `private final`** — присваиваются один раз в конструкторе
> 3. **Нет сеттеров** и любых методов, меняющих поля
> 4. **Защитное копирование (defensive copy) изменяемых полей:**
>    - в **конструкторе** — копируем входящие коллекции, массивы, `Date`, чтобы снаружи не могли изменить их через исходную ссылку
>    - в **геттерах** — не отдаём внутреннюю ссылку, а возвращаем копию или неизменяемое представление
> 5. **Методы «изменения» возвращают новый объект** (так называемые wither-методы, как `plusDays` у `LocalDate`)
>
> **Пример:**
> ```java
> public final class Order {
>     private final String number;
>     private final BigDecimal amount;
>     private final List<String> items;
>
>     public Order(String number, BigDecimal amount, List<String> items) {
>         this.number = number;
>         this.amount = amount;
>         this.items = List.copyOf(items);   // защитная копия, к тому же неизменяемая
>     }
>
>     public String getNumber() { return number; }
>     public BigDecimal getAmount() { return amount; }
>     public List<String> getItems() { return items; }   // List.copyOf уже неизменяем, менять нельзя
>
>     public Order withAmount(BigDecimal newAmount) {
>         return new Order(number, newAmount, items);    // новый объект вместо изменения
>     }
> }
> ```
>
> **Почему просто `final` у поля недостаточно:**
> `final` запрещает **переприсвоить ссылку**, но не запрещает менять **сам объект**, на который она указывает:
> ```java
> private final List<String> items = new ArrayList<>();
> items.add("x");          // работает — список изменяемый
> items = new ArrayList<>(); // ошибка компиляции — ссылку менять нельзя
> ```
> Поэтому без защитного копирования класс с `final List` **не является** неизменяемым.
>
> **Records (Java 16+):**
> `record` автоматически делает класс `final`, поля `private final`, генерирует конструктор, геттеры, `equals`, `hashCode`, `toString` и не создаёт сеттеры. Но неизменяемость **поверхностная** (shallow): если в record лежит `List`, его всё равно можно изменить. Защитную копию делают в компактном конструкторе:
> ```java
> public record Order(String number, List<String> items) {
>     public Order {
>         items = List.copyOf(items);
>     }
> }
> ```
>
> **Зачем нужны неизменяемые объекты:**
> - **потокобезопасность** без синхронизации — объект нельзя изменить, значит, нет гонок
> - **надёжные ключи** для `HashMap` и элементы `HashSet` — `hashCode` никогда не изменится (можно даже закешировать, как делает `String`)
> - **можно безопасно переиспользовать и кешировать** — пул строк, кеш `Integer` от -128 до 127
> - **проще понимать код** — объект, переданный в метод, не изменится неожиданно
>
> **Минусы:**
> - на каждое изменение создаётся новый объект → больше объектов и нагрузка на GC. Для частых изменений используют изменяемые аналоги, например `StringBuilder` вместо конкатенации `String` в цикле
>
> **Нюанс:** через рефлексию (`setAccessible(true)`) технически можно изменить даже `private final` поле, поэтому неизменяемость — это гарантия на уровне нормального использования API, а не абсолютная защита.

> [!question]- 5.1. В чём проблема, если складывать строки в цикле?
> `String` **неизменяемый**, поэтому каждое `+=` не дописывает символы в существующую строку, а **создаёт новую строку** и копирует туда все символы старой плюс новые. В цикле это даёт **O(n²)** по времени и кучу мусорных объектов для GC.
>
> **Что происходит:**
> ```java
> String report = "";
> for (String line : lines) {      // допустим, 10 000 строк
>     report += line + "\n";       // каждый раз новая строка
> }
> ```
> - 1-я итерация — копируется 1 кусок, 2-я — 2 куска, ..., n-я — n кусков
> - всего копирований примерно **n² / 2** — при 10 000 строк это десятки миллионов операций копирования
> - на каждой итерации старая строка становится **мусором** → лишняя нагрузка на сборщик мусора и память
>
> **Решение — StringBuilder:**
> ```java
> StringBuilder sb = new StringBuilder();
> for (String line : lines) {
>     sb.append(line).append("\n");
> }
> String report = sb.toString();
> ```
> `StringBuilder` — **изменяемый** буфер символов внутри. `append` дописывает в тот же массив, а когда место заканчивается, массив расширяется примерно **в 2 раза** (как у ArrayList). Итог — **O(n)** и один объект вместо тысяч. Если примерно известен итоговый размер, можно задать ёмкость сразу: `new StringBuilder(10_000)`.
>
> **StringBuilder vs StringBuffer:**
> - **StringBuilder** — не синхронизирован, быстрее. Используется почти всегда
> - **StringBuffer** — все методы `synchronized`, потокобезопасный, но медленнее. Устаревший вариант, на практике строку редко собирают из нескольких потоков
>
> **А компилятор разве не оптимизирует?**
> - конкатенацию **в одном выражении** (`"Order " + id + " total " + sum`) компилятор оптимизирует сам (до Java 9 — через StringBuilder, с Java 9 — через `invokedynamic` / `StringConcatFactory`). Её можно писать спокойно
> - а вот **в цикле** оптимизация работает только внутри одной итерации: на каждой итерации всё равно создаётся новая строка. Вынести один StringBuilder за цикл компилятор не умеет
>
> **Другие удобные способы:**
> - `String.join(", ", names)` — склеить коллекцию через разделитель
> - `names.stream().collect(Collectors.joining(", ", "[", "]"))` — со стримами, можно с префиксом и суффиксом
> - `StringJoiner` — когда нужен разделитель и собираем вручную
> - `"text".repeat(3)` (Java 11+) — повторить строку

> [!question]- 6. Как работает сборщик мусора (Garbage Collector)?
> Сборщик мусора (GC) — это часть JVM, которая **автоматически освобождает память в куче (heap)** от объектов, которые больше не используются. Разработчик сам память не освобождает (в отличие от `free` / `delete` в C/C++). Объект считается мусором, если до него **нельзя добраться** ни по одной цепочке ссылок от **GC Roots**.
>
> **Как GC понимает, что объект — мусор:**
> Не по счётчику ссылок, а по **достижимости (reachability)**. GC начинает обход от корней и помечает всё, до чего может дойти. Всё непомеченное — мусор.
>
> **GC Roots (корни):**
> - локальные переменные и параметры методов в стеках **живых потоков**
> - **статические поля** классов
> - сами активные потоки
> - ссылки из нативного кода (JNI)
>
> Поэтому **циклические ссылки не проблема**: если объекты A и B ссылаются друг на друга, но до них нельзя дойти от корней, оба будут удалены.
>
> **Базовые этапы работы:**
> 1. **Mark** — обход от GC Roots и пометка живых объектов
> 2. **Sweep** — освобождение памяти, занятой непомеченными объектами
> 3. **Compact** — сдвиг живых объектов, чтобы убрать дыры в памяти (фрагментацию). В молодом поколении вместо этого живые объекты просто **копируются** в другую область
>
> **Поколения (generational GC):**
> В основе — наблюдение: **большинство объектов живут очень недолго** (временные объекты в методах, DTO запроса). Поэтому куча делится на поколения:
> - **Young Generation** — сюда попадают новые объекты. Делится на **Eden** и две области **Survivor** (S0 и S1)
> - **Old Generation** — объекты, которые прожили долго
>
> **Как объект переходит между поколениями:**
> 1. новый объект создаётся в **Eden**
> 2. когда Eden заполнен → **Minor GC**: живые объекты копируются в Survivor, Eden очищается целиком
> 3. при каждом Minor GC выжившие объекты переезжают между S0 и S1, а их **возраст** увеличивается
> 4. объект, переживший несколько сборок (порог настраивается, максимум 15), переезжает в **Old Generation**
> 5. когда заполняется Old Generation → **Major / Full GC** — более долгая сборка
>
> Minor GC частый и быстрый (мусора в Eden много, живых мало — копировать почти нечего). Full GC редкий и дорогой.
>
> **Stop-the-World:**
> На некоторых этапах GC **останавливает все потоки приложения**, чтобы безопасно работать с памятью. Это паузы, во время которых приложение не отвечает. Главная цель современных сборщиков — сделать эти паузы как можно короче.
>
> **Основные сборщики в HotSpot:**
> - **Serial GC** — один поток, долгие паузы. Для маленьких приложений и контейнеров с 1 CPU
> - **Parallel GC** — несколько потоков, упор на максимальную пропускную способность, паузы заметные. Хорош для пакетной обработки
> - **G1 (Garbage First)** — **по умолчанию с Java 9**. Делит кучу на много небольших **регионов** и в первую очередь чистит регионы, где больше всего мусора. Старается уложиться в целевую паузу (`-XX:MaxGCPauseMillis`, по умолчанию 200 мс). Хороший баланс для большинства серверных приложений
> - **ZGC** и **Shenandoah** — почти всю работу делают **параллельно с приложением**, паузы — единицы миллисекунд и меньше, даже на очень больших кучах. Для сервисов, где важна низкая задержка
>
> **Полезные настройки:**
> - `-Xms` / `-Xmx` — начальный и максимальный размер кучи
> - `-XX:+UseG1GC`, `-XX:+UseZGC` — выбор сборщика
> - `-Xlog:gc` — логирование работы GC
>
> **Важные нюансы:**
> - **`System.gc()`** — только **просьба** запустить сборку, JVM может её проигнорировать. В нормальном коде не вызывают
> - **`finalize()`** устарел и помечен на удаление — ненадёжен и медленный. Для освобождения ресурсов используют `try-with-resources` и `AutoCloseable`
> - **GC управляет только памятью кучи.** Файлы, соединения с БД, сокеты нужно закрывать самому
> - **Утечки памяти в Java всё равно бывают** — когда на ненужный объект **остаётся ссылка**, и GC его не трогает:
>   - объекты копятся в `static` коллекции или кеше без очистки
>   - незакрытые ресурсы, неотписанные слушатели (listeners)
>   - `ThreadLocal` в пуле потоков, который не очистили
>   - «потерянные» ключи в `HashMap` из-за изменяемого `hashCode`
> - когда память закончилась и GC ничего не может освободить → **`OutOfMemoryError: Java heap space`**
> - **Metaspace** (с Java 8 вместо PermGen) хранит метаданные классов, находится вне кучи
>
> **Типы ссылок** (влияют на то, когда GC может удалить объект):
> - **strong** — обычная ссылка, пока она есть, объект не удалят
> - **soft** (`SoftReference`) — удаляется, только если памяти не хватает. Подходит для кешей
> - **weak** (`WeakReference`) — удаляется при ближайшей сборке, если других сильных ссылок нет (на этом построен `WeakHashMap`)
> - **phantom** (`PhantomReference`) — для отслеживания момента удаления объекта, используется редко

> [!question]- 6.1. Что такое GC Roots и какие они бывают?
> GC Roots — это **стартовые точки**, от которых сборщик мусора начинает обход объектов. Это ссылки, про которые JVM **точно знает, что они сейчас используются**. Объект считается живым, если до него можно дойти **по цепочке ссылок** хотя бы от одного корня. Всё остальное — мусор.
>
> Разработчик корни **не помечает и не создаёт специально** — JVM определяет их сама по своей внутренней структуре: она знает, какие потоки работают, какие методы у них в стеке и какие классы загружены.
>
> **Какие бывают GC Roots:**
> - **локальные переменные и параметры методов** в стеках **живых потоков** — пока метод выполняется, всё, на что ссылаются его переменные, живое
> - **статические поля** загруженных классов — живут, пока жив класс (обычно всё время работы приложения)
> - **активные потоки** — сами объекты `Thread`, которые ещё не завершились
> - **объекты-мониторы** — объекты, на которых сейчас удерживается `synchronized`-блокировка
> - **JNI-ссылки** — объекты, на которые ссылается нативный код (C/C++)
> - **загруженные классы и системный загрузчик классов** (ClassLoader)
>
> **Пример:**
> ```java
> public class NotificationService {
>     private static final Map<Long, Message> pending = new HashMap<>(); // static → корень
>
>     public void send(Long userId) {
>         Message msg = new Message("Hello");      // локальная переменная → корень, пока метод работает
>         msg.setAttachment(new File("a.pdf"));    // File живой: корень → msg → attachment
>
>         Message draft = new Message("Draft");
>         draft = null;                            // на этот объект никто не ссылается → мусор
>     }
>     // метод завершился → msg пропала из стека → Message и File стали мусором
>     // (если бы мы положили msg в pending, он остался бы живым через static)
> }
> ```
>
> **Простая аналогия:** корни — это **якоря**. Пока объект через цепочку ссылок привязан хотя бы к одному якорю, GC его не трогает. Оторвался от всех якорей — будет удалён, даже если сам ссылается на другие объекты или другие объекты ссылаются на него (поэтому **циклические ссылки** не мешают сборке).
>
> **Связь с утечками памяти:** почти любая утечка в Java — это объект, который **случайно остался достижим от корня**. Чаще всего через `static`-коллекцию, кеш без очистки, `ThreadLocal` в пуле потоков или неотписанный слушатель. В дампе памяти (heap dump) такие объекты ищут именно по **пути до GC Root** — инструменты вроде Eclipse MAT или VisualVM показывают, какая цепочка ссылок держит объект живым.

> [!question]- 7. Что такое synchronized-блок и чем он отличается от synchronized-метода?
> `synchronized` — ключевое слово для **взаимного исключения** потоков: код внутри может выполнять **только один поток одновременно** для одного и того же объекта-замка. Работает через **монитор** (intrinsic lock) — он есть у **каждого объекта** в Java.
>
> **Что даёт synchronized:**
> - **атомарность** — пока один поток внутри, остальные, пытающиеся взять тот же монитор, **ждут** (состояние `BLOCKED`)
> - **видимость** — при выходе из блока изменения сбрасываются в общую память, а следующий поток, вошедший по тому же монитору, гарантированно их увидит (отношение **happens-before**)
> - **реентерабельность** — поток, уже держащий монитор, может снова войти в synchronized по тому же объекту (например, один synchronized-метод вызывает другой) и не заблокирует сам себя
> - монитор **освобождается автоматически** при выходе из блока, в том числе при исключении
>
> **Synchronized-метод** — блокируется **весь метод**, а замок выбирается автоматически:
> ```java
> public synchronized void deposit(BigDecimal amount) {   // замок — this
>     balance = balance.add(amount);
> }
>
> public static synchronized void nextId() {             // замок — Account.class
>     counter++;
> }
> ```
> - обычный метод → замок на **`this`** (текущий объект)
> - статический метод → замок на **объекте класса** (`Account.class`)
>
> **Synchronized-блок** — блокируется **только часть кода**, и замок указываем **сами**:
> ```java
> private final Object lock = new Object();
>
> public void deposit(BigDecimal amount) {
>     validate(amount);                 // без блокировки — потоки выполняют параллельно
>     log.info("Deposit {}", amount);
>
>     synchronized (lock) {             // блокируется только критическая секция
>         balance = balance.add(amount);
>     }
> }
> ```
>
> **Отличия:**
>
> | | synchronized-метод | synchronized-блок |
> |---|---|---|
> | Что блокируется | весь метод | только нужный участок кода |
> | Объект-замок | `this` или `Class` — выбрать нельзя | любой объект на выбор |
> | Гибкость | меньше | можно сделать несколько разных замков для независимых данных |
> | Производительность | потоки дольше ждут, т.к. блокировка шире | лучше — блокировка держится минимальное время |
> | Байткод | флаг `ACC_SYNCHRONIZED` у метода | инструкции `monitorenter` / `monitorexit` |
>
> **Почему на практике чаще используют блок с приватным замком:**
> - **меньше область блокировки** — валидация, логирование, вызовы других сервисов идут параллельно, под замком только изменение общих данных
> - **несколько независимых замков** — например, один для баланса, другой для истории операций. Потоки, работающие с разными данными, не мешают друг другу
> - **инкапсуляция** — `this` доступен снаружи, и чужой код может сделать `synchronized (account)` и случайно заблокировать наш объект. Приватный `lock` никто снаружи взять не может
>
> **Частые ошибки:**
> - **статический и обычный synchronized-методы не исключают друг друга** — у них разные замки (`Class` и `this`), поэтому они могут выполняться одновременно
> - **синхронизация на разных объектах** — если каждый поток создаёт свой экземпляр и блокирует `this`, защиты общего `static` поля нет
> - **замок на String-литерале или Integer** (`synchronized ("lock")`) — из-за пула строк и кеша `Integer` этот же объект может использоваться в совсем другом месте программы
> - **замок на поле, которое переприсваивается** — после присваивания потоки блокируют уже разные объекты. Поле-замок должно быть `final`
> - **долгие операции внутри** (HTTP-запросы, запросы к БД) — остальные потоки всё это время ждут
> - **виртуальные потоки:** в Java 21 блокировка внутри `synchronized` «прикалывает» (pinning) виртуальный поток к carrier-потоку. Исправлено в Java 24, для Java 21 рекомендуется `ReentrantLock`
>
> **Альтернативы:**
> - `ReentrantLock` — то же самое, но с `tryLock()` (с таймаутом), прерываемым ожиданием, «честной» очередью и несколькими условиями (`Condition`). Нужно не забыть `unlock()` в `finally`
> - `AtomicInteger`, `AtomicLong`, `LongAdder` — для простых счётчиков без блокировок
> - `ConcurrentHashMap` и другие concurrent-коллекции — потокобезопасность уже внутри

> [!question]- 8. Что такое ООП?
> ООП (объектно-ориентированное программирование) — это **подход к написанию программ**, при котором программа строится из **объектов**. Объект объединяет в себе **данные (состояние, поля)** и **поведение (методы)**, которые с этими данными работают. Объекты создаются по шаблону — **классу**.
>
> Например, класс `Order` описывает, какие поля есть у заказа (номер, сумма, статус) и что с ним можно сделать (`pay()`, `cancel()`). Каждый конкретный заказ — это объект этого класса.
>
> **Четыре основных принципа:**
>
> **1. Инкапсуляция** — объект **скрывает своё внутреннее состояние** и даёт работать с ним только через свои методы. Поля делаются `private`, а изменение идёт через методы, которые проверяют правила.
> ```java
> public class Wallet {
>     private BigDecimal balance = BigDecimal.ZERO;
>
>     public void withdraw(BigDecimal amount) {
>         if (amount.compareTo(balance) > 0) {
>             throw new IllegalStateException("Недостаточно средств");
>         }
>         balance = balance.subtract(amount);
>     }
> }
> ```
> Снаружи нельзя просто написать `wallet.balance = -500` — объект сам защищает свою целостность.
>
> **2. Наследование** — класс может **унаследовать** поля и методы другого класса (`extends`) и расширить или изменить их. Позволяет переиспользовать код и строить иерархии «является» (is-a).
> ```java
> public class Notification { void send() { ... } }
> public class EmailNotification extends Notification { ... }
> ```
> В Java класс может наследовать **только один** класс, но реализовывать **много интерфейсов**.
>
> **3. Полиморфизм** — возможность работать с объектами разных классов **через общий тип**, при этом каждый объект ведёт себя по-своему.
> ```java
> List<Notification> list = List.of(new EmailNotification(), new SmsNotification());
> for (Notification n : list) {
>     n.send();   // вызовется своя реализация у каждого объекта
> }
> ```
> - **динамический** (во время выполнения) — **переопределение** методов (`@Override`). Какой метод вызвать, JVM решает по реальному типу объекта
> - **статический** (во время компиляции) — **перегрузка** методов: одно имя, разные параметры (`print(int)`, `print(String)`)
>
> **4. Абстракция** — выделяем **только существенное** и скрываем детали реализации. Описываем, **что** объект умеет, а не **как** он это делает. В Java — через **интерфейсы** и **абстрактные классы**.
> ```java
> public interface PaymentGateway {
>     PaymentResult charge(BigDecimal amount);
> }
> ```
> Код, который использует `PaymentGateway`, не знает и не должен знать, Kaspi это, Stripe или заглушка для тестов.
>
> **Зачем нужно ООП:**
> - код ближе к предметной области — сущности программы похожи на реальные (заказ, клиент, платёж)
> - **переиспользование** кода через наследование и композицию
> - **легче менять и расширять** — новую реализацию можно добавить, не трогая код, который работает через интерфейс
> - **проще поддерживать** большие системы — ответственность разделена между классами
>
> **Минусы и нюансы:**
> - глубокие иерархии наследования становятся хрупкими: изменение в родителе ломает наследников. Поэтому есть правило **«композиция предпочтительнее наследования»** — чаще объект содержит другой объект (has-a), чем наследуется от него
> - легко переусложнить: лишние абстракции, интерфейсы с одной реализацией «на всякий случай»
> - для чисто вычислительных задач и обработки потоков данных функциональный стиль (Stream API, лямбды) часто удобнее. Java поддерживает оба подхода
>
> **Связь с SOLID:** принципы SOLID — это набор правил, как **правильно** применять ООП, чтобы код оставался гибким: единственная ответственность, открытость для расширения, подстановка Лисков, разделение интерфейсов, инверсия зависимостей.

> [!question]- 8.1. Как вы представляете абстракцию? Например, есть магазин с разными отделами — как это спроектировать?
> Абстракция — это выделить **общее и существенное**, что есть у всех отделов, и **скрыть детали**, которые у каждого отдела свои. Магазин должен знать, **что** умеет любой отдел, но не должен знать, **как** именно каждый отдел это делает.
>
> **Как рассуждать:**
> 1. **Что общего у всех отделов?** — у каждого есть название, сотрудники, товары; каждый умеет принять товар, продать товар, оформить возврат, посчитать выручку
> 2. **Что у каждого своё?** — продуктовый отдел проверяет срок годности, электроника оформляет гарантию, одежда разрешает обмен по размеру в течение 14 дней
> 3. **Общее** выносим в абстракцию (абстрактный класс или интерфейс), **различия** — в конкретные классы
>
> **Абстрактный класс — общий «скелет» отдела:**
> ```java
> public abstract class Department {
>     private final String name;
>     private final List<Employee> employees = new ArrayList<>();
>
>     protected Department(String name) { this.name = name; }
>
>     // общее поведение — одинаковое для всех отделов
>     public BigDecimal sell(Product product, int quantity) {
>         checkAvailability(product, quantity);
>         BigDecimal price = calculatePrice(product, quantity);   // своя логика у каждого
>         recordSale(product, quantity, price);
>         return price;
>     }
>
>     // то, что каждый отдел обязан реализовать сам
>     protected abstract BigDecimal calculatePrice(Product product, int quantity);
>     public abstract boolean canReturn(Product product, LocalDate purchaseDate);
>
>     private void checkAvailability(Product product, int quantity) { ... }
>     private void recordSale(Product product, int quantity, BigDecimal price) { ... }
> }
> ```
>
> **Конкретные отделы — свои детали:**
> ```java
> public class GroceryDepartment extends Department {
>     protected BigDecimal calculatePrice(Product p, int qty) {
>         // скидка 30% на товары, у которых завтра истекает срок годности
>     }
>     public boolean canReturn(Product p, LocalDate date) {
>         return false;                       // продукты не возвращаются
>     }
> }
>
> public class ElectronicsDepartment extends Department {
>     protected BigDecimal calculatePrice(Product p, int qty) {
>         // цена + опционально расширенная гарантия
>     }
>     public boolean canReturn(Product p, LocalDate date) {
>         return date.plusDays(14).isAfter(LocalDate.now());
>     }
> }
> ```
>
> **Интерфейсы — для дополнительных «умений»,** которые есть не у всех отделов:
> ```java
> public interface Deliverable    { DeliveryInfo arrangeDelivery(Order order); }   // доставка: электроника, мебель
> public interface Refrigerated   { void checkTemperature(); }                     // холодильники: продукты
> public interface Installable    { void scheduleInstallation(Order order); }      // установка: бытовая техника
>
> public class ElectronicsDepartment extends Department implements Deliverable, Installable { ... }
> public class GroceryDepartment extends Department implements Refrigerated { ... }
> ```
>
> **Магазин работает только с абстракцией:**
> ```java
> public class Store {
>     private final List<Department> departments;
>
>     public BigDecimal dailyRevenue() {
>         return departments.stream()
>             .map(Department::getRevenue)
>             .reduce(BigDecimal.ZERO, BigDecimal::add);
>     }
> }
> ```
> `Store` не знает, какие отделы есть и как они считают цены. Добавили «Детский отдел» — создали новый класс, а `Store` не изменился.
>
> **Почему именно так:**
> - **абстрактный класс** — когда у отделов есть **общее состояние** (название, сотрудники) и **общая логика** (порядок продажи). Отношение «является»: продуктовый отдел **является** отделом
> - **интерфейс** — когда это **способность**, которая есть только у части отделов и может сочетаться (отдел может и доставлять, и устанавливать). Класс может реализовать много интерфейсов, но наследоваться только от одного класса
> - метод `sell` в базовом классе задаёт **общий порядок шагов**, а детали отдают наследникам — это паттерн **Шаблонный метод (Template Method)**
>
> **Абстракция на разных уровнях:**
> - **класс** — `Department` скрывает, как считается цена
> - **метод** — `sell()` скрывает проверку наличия и запись продажи
> - **сервис** — магазин вызывает `PaymentGateway.charge()` и не знает, через какой банк идёт оплата
> - **архитектура** — отделы-департаменты компании (склад, бухгалтерия, доставка) общаются через чёткие API, не зная внутреннего устройства друг друга. На уровне микросервисов это та же идея
>
> **Чем абстракция отличается от инкапсуляции:**
> - **абстракция** — про то, **что показать**: выделяем важное и задаём контракт (какие методы есть у любого отдела)
> - **инкапсуляция** — про то, **как защитить**: прячем поля и внутреннюю реализацию за `private`, чтобы их нельзя было испортить снаружи
